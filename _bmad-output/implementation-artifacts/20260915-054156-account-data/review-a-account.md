## A-1 — An outgoing mood sync can finish into the replacement account session

- **Severity:** medium (P2). **Confidence:** high for the store race; no browser reproduction was attempted.
- **DW relationship:** mood account-race requirement; same identity/session invariant as DW-100 and DW-101. No existing dedicated DW number was found for this particular action.
- **Files/symbols:** `src/stores/slices/moodSlice.ts`, `syncPendingMoods`, lines 205–305: missing capture at entry; post-await writes at 255–257, 282–288 and 297–302; fresh-session follow-up actions at 265 and 279. Reset contract: `src/stores/slices/authSlice.ts`, `signedOutState`, lines 61–73. Production callers include `src/App.tsx:447`, `:478`, `:488` and `src/components/MoodTracker/MoodTracker.tsx:278`.
- **Concrete evidence:** `addMoodEntry`, `updateMoodEntry`, `loadMoods`, `updateSyncStatus` and `fetchPartnerMoods` now check both user ID and session version, but `syncPendingMoods` never captures either. After awaiting `withSyncLock`, it calls the current store’s loaders and unconditionally writes a new `lastSyncAt` and `isSyncing: false`. Its failure and skipped branches also unconditionally clear the live flag.
- **Executed reproduction:** transpiled the actual current `moodSlice.ts` to CommonJS entirely in memory using TypeScript, injected a deferred sync service and non-network service stubs, and instantiated its real slice factory. Started a sync as account A/version 1, replaced state with account B/version 2 and B status `{ pendingMoods: 7, isSyncing: true, lastSyncAt: 2000-01-01 }`, then resolved A’s service result. B’s final status became `{ pendingMoods: 0, isSyncing: false, lastSyncAt: <current time> }`. The pending count change comes from the stale operation invoking B’s new loader (stubbed empty); the unconditional flag clear and timestamp overwrite are independent of that stub value. No implementation file or real service state was changed by this probe.
- **Trigger:** A’s background/retry sync remains pending while A signs out and B signs in, or while A signs out and signs back in. The old sync then succeeds, rejects, or returns skipped. A successor sync/status in the new session can be overwritten; even with no successor, a signed-out reset receives a fresh sync timestamp from the dead session.
- **User impact/root cause:** the new session can show that synchronization has completed when its own work has not finished; the old completion also clears the flag used to suppress duplicate same-tab sync attempts. Account-scoped completion state is written without checking which session owns it. This is a status/concurrency bug; this review did not establish disclosure of another account’s mood text or database data loss.
- **Introduced vs. pre-existing:** pre-existing at the exact baseline; the `syncPendingMoods` body is unchanged. It remains a gap against the explicitly requested mood account-race invariant despite the adjacent action fixes. Treat it as a follow-up if this review’s acceptance boundary excludes unchanged actions.
- **Recommendation:** capture `{ userId, authSessionVersion }` before starting the sync and recheck before each continuation that invokes a new account action or writes status, including skipped/error exits. A stale completion must leave the new session’s spinner, count and timestamp untouched. Keep persistence of already-started work governed by its original owner; suppress only stale UI follow-through.
- **Verification/regression:** add deferred success, rejection and skipped tests for A→B and A→signed out→A. Seed a recognizable successor status, resolve/reject the old operation, and assert the entire successor status is unchanged and no successor loaders/partner refresh are launched by the stale request. Include a same-account token-refresh control to ensure an uninterrupted session still receives completion.
- **Uncertainties/assumptions:** the executed probe replaces identity/version directly to isolate the slice; existing authentication code confirms real sign-out/switch advances the version and resets this status. Network-lock scheduling and the rendered browser indicator were not measured. The same-account variant follows directly from the complete absence of any identity/version check, but was not separately executed in this probe.
