topic: Unify My-Love data storage: server as source of truth, per-account offline copy for every screen, two save modes
updated: 2026-09-24T18:45
---

- (direction) Owner wants the app to work offline, with the offline data always coming from the server; wants one storage approach for all data instead of today's four (server-only; server-first with local mirror; offline-first mood; bundled).
- (decision) Supabase is the source of truth for all account and couple data; the device's local copy is only ever filled from the server or from the user's own confirmed/queued writes.
- (decision) Reads use stale-while-revalidate: every screen renders the local copy immediately and refreshes it from the server; chosen over network-first because weak signal would otherwise stall screens on timeouts.
- (decision) Two save modes only: 'save offline, send later' (optimistic, queued) for mood and love notes; 'needs a connection' (pessimistic, refused offline) for everything else.
- (decision) Photos cache under a size limit (thumbnails and recent items), not every full-size image.
- (decision) Local copies refresh when the connection returns, not only at app start.
- (decision) The one-time local-data upload and GitHub Pages bridge are removed in a separate prior change (owner confirmed no old phone data to keep); this spec assumes that code is gone.
- (decision) Slug unified-data-storage; express distillation — input is rich from the owner conversation, gaps become open questions.
- (direction) Break into loop-sized stories; AGENTS.md budgets 2M tokens per story, keep story specs short and split large ones.
- (note) Brownfield mapped 2026-09-23 at 023ea7fd by two read-only investigations; findings in brownfield.md. Offline today: own mood queued; anniversaries/favorites/custom messages readable (writes refused); bundled messages. Photos, notes, pokes/kisses, events, partner mood, partner profile are memory-only and fail offline.
- (capability) CAP-1 intent: every screen showing account or couple data renders its last saved copy immediately, online or offline, and replaces it with server data when reachable. success: after one online session then offline, each covered screen shows the data last loaded.
- (capability) CAP-2 intent: local copies refresh on app start/sign-in, when the connection returns, and on Realtime events. success: a server change made while the device was offline appears after reconnect without a reload.
- (capability) CAP-3 intent: mood entries and love-note text save offline, show immediately as pending, and send automatically once online, in order, exactly once. success: three notes sent offline reach the partner after reconnect, in order, no duplicates across retries and reloads.
- (capability) CAP-4 intent: every other write is refused up front when offline with a clear needs-a-connection message and no local change. success: each such control offline shows the message and the local copy is unchanged.
- (capability) CAP-5 intent: photos are viewable offline within a device storage limit: the gallery list plus the most recent photos images; older ones show a placeholder. success: offline, recent photos display and the photo cache stays under its limit.
- (capability) CAP-6 intent: own mood history is filled from the server, so a new device shows past moods. success: sign-in on a fresh device shows prior moods in the calendar.
- (capability) CAP-7 intent: local copies are per account; one account never sees another account cached data on a shared device, and sign-out removes the account cached copies but keeps its unsent queued writes. success: A signs out, B signs in, no A data appears; A signs back in and A pending writes still send.
- (capability) CAP-8 intent: when showing saved data offline, the user can tell they are offline and data may be out of date. success: offline, the app shows an offline indicator on every data screen.
- (constraint) One shared local-copy mechanism for all data kinds; no feature keeps a bespoke cache or loads Supabase straight into screen state. Owner goal: one method, fewer rules for agents to get wrong.
- (constraint) Local copies are filled only from server responses, Realtime events, or the user own writes (confirmed or queued).
- (constraint) Queued writes reuse one client-generated key across attempts backed by a DB UNIQUE constraint and upsert ignoreDuplicates: mood keeps (user_id, created_at), love notes keep idempotency_key (AGENTS.md).
- (constraint) IndexedDB changes only in src/services/dbSchema.ts: bump DB_VERSION, gate each branch on store existence (AGENTS.md). The dead photos store is reused or dropped there.
- (constraint) New Realtime work goes through moodSyncService registry or sendEphemeralBroadcast; never supabase.channel directly (AGENTS.md).
- (constraint) Post-await store writes re-check {userId, authSessionVersion}; new account-scoped state is added to signedOutState() in the same change (AGENTS.md).
- (constraint) Images are cached by storage path, never by signed URL: signed URLs change on every signing and expire after 3600 s.
- (constraint) A queued love note must not depend on a network partner lookup at send time (getPartnerId returns null offline); a failed read is never treated as unlinked (lookupPartnerId, AGENTS.md).
- (constraint) Offline behaviour lives in app code, testable with Playwright setOffline: E2E runs vite in dev mode with no service worker. The service worker may add to it but is never required.
- (constraint) Zustand persist version stays 0; E2E fixtures pin it.
- (decision) Non-goals: offline create/edit/delete for anything except mood and love-note text; conflict handling beyond last-write-wins; changes to bundled daily messages; offline sign-in or sign-up.
- (assumption) Photo thumbnails means caching the existing compressed images (max 2048 px); no new server-side thumbnail generation.
- (assumption) The note queue drains while the app is open (start, online event, interval); mood keeps its existing service-worker Background Sync, notes do not need one.
- (question) Photo cache limit: recommend the most recent 50 photos, capped at 100 MB, oldest evicted first.
- (question) Love notes with a photo offline: recommend needs-a-connection; only text notes queue.
- (question) Device settings (start date, partner name, notification time) live only on the phone: recommend leaving them out of this spec as a separate later change.
- (question) Sign-out: recommend deleting the account cached copies (keeping unsent writes), since sign-in needs a connection anyway.
