- (direction) Origin: this feature was proposed by Sallvain while reviewing spec-dynamic-events, as an alternative to full live sync. Their words: "what if we set up a way for an in app notification to pop up when a partner adds something that notifies the other partner? Then when the partner that received the message taps on the notification it brings the user to whatever the notification was for and does the reload for them." Scoped by them across love notes, photos and the forthcoming events feature.
- (decision) Split into its own spec folder rather than folded into spec-dynamic-events, because it spans love notes, photos and events and would otherwise leave the events spec mostly about things other than events. spec-dynamic-events already absorbed a navigation redesign at Sallvains request; a second cross-cutting feature would make it unreadable. spec-dynamic-events consumes this one for the events case.
- (direction) Sallvain approved BOTH halves — "id want both" — after asking what a persistent badge was. Agreed build order is badge first, toast second, because the badge is both cheaper and higher-value for a long-distance couple.
- (decision) Core architectural property, and the reason this design was preferred over live sync: the broadcast carries a SIGNAL, not DATA. Nothing merges a payload into a list; the tap triggers an ordinary refetch and the server stays the single source of truth. That removes the last-writer-wins reducer, the tombstone list and the ordering discipline that made full sync a 3-5 day job, and it downgrades a dropped message from DIVERGENT to merely STALE.
- (constraint) Web Push is OUT of scope and no scaffolding for it should be built. Sallvain: "yes i do want lock screen notifications eventually, but thats after a future migration to an actual app instead of a webapp (i want this to eventually be an actual app and not a pseudo app thats added from a website, but thats for another time)." The app today has none of it — grep over src/ for pushManager, PushSubscription, showNotification, Notification.requestPermission and VAPID returns nothing, and src/sw.ts registers only :114 "sync" and :355 "activate". Building push scaffolding now would target a platform not yet chosen.
- (constraint) The watermark lives in its OWN table, not as a viewed flag on each feature table. love_notes deliberately carries no UPDATE policy — 20260727000000_love_notes_idempotency.sql:15-19 "Deliberately NOT paired with an UPDATE policy. love_notes grants only INSERT and SELECT ... Adding UPDATE purely to support merge-duplicates would also let a user edit notes they had already sent" — and a viewed column would need exactly that grant. photos likewise has only SELECT/INSERT/DELETE policies (20251203190800:50-73), and a photos.viewed written by the non-owner partner would need a new UPDATE policy on someone elses row.
- (note) The only prior art for an unseen count is interactions.viewed — a per-ROW flag on one table (20251203000001_create_base_schema.sql:154 "viewed BOOLEAN DEFAULT false,", indexed at 20251206024345:73, recipient UPDATE policy at :175-178, written via interactionService markAsViewed and counted at interactionsSlice.ts:188-190). It does not generalise for the two reasons above, so this spec uses a per-user watermark instead. No last_seen/last_read marker exists anywhere yet: grep over src/ and supabase/migrations/ returns nothing.
- (note) Why badge-before-toast, stated so downstream does not reorder it. A backgrounded PWA is frozen by the OS and its Realtime socket drops within seconds, so the toast fires only when both partners have the app FOREGROUNDED at the same instant — and, before the app-level hoist, only when the receiver is parked on the exact tab, since every realtime receiver today is mounted inside a lazy tab-gated view. An agent put the ephemeral-only value at less than half, and closer to a tenth as the app stands. The badge, by contrast, fires every time the user opens the app after anything happened, and needs no realtime at all.

App.tsx:10 and :522 both record "PokeKissInterface moved to PartnerMoodView", so the app-level notification slot was deliberately vacated.

That is exactly the behaviour this spec generalises, differing only in that the refetch is triggered by a tap rather than automatically.

- (question) Badge placement is genuinely unresolved and interacts with the other spec. spec-dynamic-events/navigation.md replaces the fixed bottom tab bar with a hamburger-triggered tray, and a badge on a destination inside a CLOSED tray is invisible — which defeats the whole point of the badge. The likely answer is an aggregate indicator on the hamburger button itself plus per-destination counts inside the open tray, but that needs deciding, and it is a dependency between the two specs in the direction nobody expected: the navigation redesign constrains the notification feature.
- (question) What clears a badge? Visiting the destination is the obvious rule but is not obviously right — glancing at the Photos tab is not the same as having looked at eleven new photos. interactions clears per row via markAsViewed; a watermark clears everything at once. Needs a decision before the store actions are written.
- (constraint) The counts depend on a linked partner, which is nullable. partnerSlice.ts:23 declares "partner: PartnerInfo | null;" defaulting to null at :44 and loaded at :61 "const partner = await partnerService.getPartner();" then :72 "set({ partner, isLoadingPartner: false });". So every count query must handle the unlinked case — with no partner there is nothing to count, and the badge must render nothing rather than zero-with-a-dot or a spinner. :57 also carries a warning about a reset race: "write the previous accounts partner straight back over the reset", so the identity guard applies here as everywhere.

- (constraint) The notes count query MUST carry an explicit to_user_id filter — RLS alone counts the wrong thing.
